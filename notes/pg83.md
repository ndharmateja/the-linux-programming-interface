You have asked the exact question that separates surface-level programmers from systems engineers. The concept of a file being legally 5 Gigabytes in size while consuming exactly 0 bytes of physical disk space sounds like a magic trick.

Let’s clear up a slight misunderstanding about file size first, and then pull back the curtain on how the Linux kernel pulls off this illusion.

---

## The Clarification: Apparent Size vs. Physical Size

To clear up the confusion: file holes **do** count toward the reported file size (called the **nominal or apparent size**), but they **do not** count toward the **physical size** on the disk platter or SSD.

If you create a file, seek 1 Gigabyte out, and write the letter `"A"`, Linux registers two entirely different metrics for that file:

* **Apparent Size (`ls -l`):** `1,000,000,001 bytes`. If you pass this file to a Python script or look at it in a file explorer, it claims to be 1 GB.
* **Physical Disk Allocation (`du` or `stat`):** `4,096 bytes` (exactly 1 physical disk block used to hold that single letter `"A"`).

---

## How It Works: The Block Mapping Illusion

You asked: *Does it explicitly store somewhere that these ranges are null bytes? How does it know while reading?*

The filesystem **never stores a single null byte on the disk** for a hole. It doesn't even store a list saying "here are null bytes." Instead, it uses **omission**.

Every file on Linux is managed by an **inode** (an index node), which contains a metadata table mapping the file’s logical blocks to actual physical blocks on the hard drive.

Imagine a file system where disk blocks are 4 KB each. If you write data normally, the kernel populates the map sequentially. But if you jump past the end of the file using `lseek()` and write data, the kernel leaves the middle entries completely empty.

### The Inode Map Table Under the Hood:

```text
Logical File Block   | Physical Disk Block Address
---------------------------------------------------
Block 0 (0 - 4KB)     | Disk Block #58210
Block 1 (4 - 8KB)     | NULL (No disk block allocated!) -> This is the hole
Block 2 (8 - 12KB)    | NULL (No disk block allocated!) -> This is the hole
Block 3 (12 - 16KB)   | Disk Block #58211

```

*(Note: Modern filesystems like `ext4` or `XFS` optimize this even further using "extents," where they store a range list like: "Logical blocks 0-1 map to Disk block X; Logical blocks 2-1000 are a HOLE; Logical blocks 1001-1002 map to Disk block Y.")*

---

## What Happens During a `read()`?

When your application calls `read()` on a file with holes, the disk hardware is completely bypassed for the hole sectors.

1. Your program asks to read 4096 bytes starting at file offset `4096` (which lands cleanly in **Logical Block 1**).
2. The kernel's VFS (Virtual File System) layer checks the file's inode block map for Logical Block 1.
3. The kernel sees that the physical disk address for this block is **`NULL`** (or marked as an unallocated extent).
4. **The Epiphany:** The kernel does *not* issue a read command to the physical SSD controller. Instead, the kernel instantly executes a memory-clearing operation (like `memset`) directly inside your application’s provided user-space buffer, filling it with `0x00` bytes (null bytes).
5. The `read()` call returns `4096` to your program, pretending it read those bytes straight off the iron platter.

The application thinks it is reading file data; the kernel knows it is just playing make-believe in RAM.

## Breaking Down the Rest of the TLPI Text

Now that you have the mental model of unallocated blocks, the rest of Kerrisk's fine-print points click into place perfectly:

### 1. The Block Boundary Edge-Case

Filesystems cannot allocate half a block. If a physical block size is 4096 bytes, and your hole ends at byte 3000 because you wrote data at byte 3001, the kernel *must* allocate a real, physical 4096-byte block on the disk to hold that data. The remaining 3000 bytes at the front of that specific block are physically padded with zeros on the disk platter.

### 2. Native vs. Non-Native (ext4 vs. VFAT/FAT32)

Advanced Linux filesystems (`ext4`, `Btrfs`, `XFS`) support sparse files out of the box because their inode architecture allows blocks to point to `NULL`. Older or simpler filesystems like Microsoft's `FAT32` (used on many USB thumb drives) do not have a concept of unallocated index entries. If you try to create a 1 GB hole on a FAT32 drive, the filesystem driver is forced to physically write 1 Gigabyte of actual zeros to the flash cells, freezing your program while it waits for the hardware I/O to finish.

### 3. Why `posix_fallocate()` Exists

Imagine you are building a database engine. You create a massive, sparse file with 10 Terabytes of logical holes, intending to fill it up with user data over the next year.

Because holes take up zero disk space, the creation succeeds instantly. However, six months later, the physical hard drive runs out of space because other users filled up the server. The next time your database tries to execute a normal `write()` into one of its file holes, the kernel will fail to find an available disk block to link to the inode table. Your `write()` call will catastrophically fail with **`ENOSPC` (Error No Space)**.

To prevent this nightmare, you use `posix_fallocate()`. It forces the kernel to talk to the disk controller *immediately* and pre-allocate physical, empty blocks to the entire range of the file. It fills the holes on disk ahead of time, ensuring that future `write()` calls are guaranteed to succeed without risking unexpected hardware exhaustion.
