This is one of the coolest implementation details in systems programming, and it highlights a massive architectural clash between the **historical design of the C language** and the modern reality of **multi-threaded execution**.

To understand why the first approach is slow, we have to look under the hood at how `errno` changes when you go from a single-threaded program to a multi-threaded one.

---

## 1. The Global `errno` Problem

Historically, in standard C, `errno` was just a plain old global integer variable.

```c
// In traditional, single-threaded glibc
int errno; 

```

If a system call failed, the kernel wrote the error code into this global variable, and your program read it.

But imagine what happens if you have **Thread A** and **Thread B** running at the same time in a single process. Thread A makes a system call that fails and sets `errno` to `EACCES` (Permission Denied). Right before Thread A can check `errno`, the CPU schedules Thread B. Thread B makes a system call that fails and overwrites the exact same global `errno` with `ENOENT` (File Not Found). When Thread A resumes, it reads the wrong error code!

---

## 2. The Multi-Threaded Fix: `errno` as a Macro

To prevent threads from trampling over each other's error codes, POSIX requires that **each thread must have its own private `errno**`.

To make this happen without changing the syntax for millions of lines of existing C code, the C library (`glibc`) changes what the word `errno` actually means. In a threaded program, `errno` is no longer a variable. It is a **preprocessor macro** that expands into a function call.

It looks something like this behind the scenes:

```c
// In modern, multi-threaded <errno.h>
extern int *__errno_location(void);
#define errno (*__errno_location())

```

When you write `errno = pthread_create(...)`, the preprocessor secretly turns your code into this:

```c
(*__errno_location()) = pthread_create(&thread, NULL, func, &arg);

```

The function `__errno_location()` looks at the currently executing thread, finds that thread's unique Thread-Local Storage (TLS) memory space, and returns a pointer to *that specific thread's* error integer. The outer `*` dereferences it so you can read or write to it (an "lvalue").

---

## 3. Why the First Approach is Slow

Now look back at the first code snippet:

```c
errno = pthread_create(&thread, NULL, func, &arg); // Function Call 1 (__errno_location)
if (errno != 0)                                    // Function Call 2 (__errno_location)
    errExit("pthread_create");

```

Because `errno` is a macro hiding a function call, this code performs **two hidden function calls** just to assign and check the value.

Worse yet, accessing Thread-Local Storage via a function call isn't always cheap; it can involve calculating memory offsets relative to thread registers, adding unnecessary CPU cycle overhead to what should be a simple variable check.

---

## 4. Why POSIX Thread Functions are Different

Unlike traditional Linux system calls (like `open()` or `read()`), which return `-1` and force you to use `errno`, **POSIX thread functions (`pthread_*`) never use `errno` directly.**

Instead, they return the error code **directly as their integer return value**. If a pthread function succeeds, it returns `0`. If it fails, it returns a positive error number (like `EPERM` or `EAGAIN`).

---

## 5. The Elegant, Efficient Solution

Knowing this, look at Kerrisk's optimized snippet:

```c
int s;
s = pthread_create(&thread, NULL, func, &arg); // Direct return value captured in a CPU register/stack
if (s != 0)                                    // Lightning-fast integer comparison
    errExitEN(s, "pthread_create");

```

By capturing the return value directly into a local stack variable (`s`), you bypass the hidden `__errno_location()` function call entirely during the success path.

* **The standard path (Success):** `s` is `0`, the `if` condition is false, and you move on. Total hidden function calls: **Zero**.
* **The exceptional path (Failure):** Only if an error actually happens do you pass `s` into `errExitEN()`, which handles printing the error.

Since 99% of the time your code will succeed, the second pattern keeps your main program loop highly optimized and free of hidden thread-local memory lookups.
